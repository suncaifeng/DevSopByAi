## Route and counter branches

Routing checks failed results in this order:

| Condition | Decision |
|---|---|
| DSL has blockers, unresolved issues, blocking markers, or blocked status | `REPAIR_SPEC` directly |
| Stuck-loop check fires | Test, spec-conflict, or validation errors go through repair/regeneration; other error types go to `FATAL` |
| `TEST_FAILURE` | `RETRY_CODEX` if retry budget permits; otherwise `REPAIR_SPEC` if repair budget permits, else `FATAL` |
| `SPEC_CONFLICT` | `REPAIR_SPEC` if repair budget permits, else `REGENERATE_SPEC` |
| `VALIDATION_ERROR` | `REPAIR_SPEC` if repair budget permits, else `FATAL` |
| `CODEX_ERROR` | `RETRY_CODEX` if retry budget permits, else `FATAL` |
| `ENV_ERROR` or other error type | `FATAL` |

These branches and their precedence are implemented in `route_decision`, `_route_stuck_loop`, `_repair_or_regenerate`, and `_repair_or_fail`. - The exact route cannot be determined without subprocess output or exception details, the DSL contents, prior history, and run policy. For nonzero exits, classifier keyword matching and its order determine the error type; text that matches multiple categories takes the first matching category.
