The timeout helper reads `metadata["timeout_seconds"]`, accepts it when it is a positive `int`, and otherwise uses the 300-second default. The input validator checks readiness, DSL, workspace, and run policy, but does not validate this metadata value. ### Routing and recovery

`main` appends each result to history before calling `route_decision`. Routing checks success first, then blocking DSL state, then the stuck-loop detector, and only after that classifies failures by error type. A non-blocked `CODEX_ERROR`, including a caught timeout, routes to `RETRY_CODEX` while retry and cycle budgets allow; otherwise it routes to `FATAL`. ([history and routing order](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-B-attempt1/main.py:39>), [route precedence](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-B-attempt1/routing_system.py:33>), [CODEX_ERROR handling](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-B-attempt1/routing_system.py:86>), [retry budget](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-B-attempt1/contracts.py:270>))

**Source-derived inference:** The stuck-loop window is three error entries, but the detector takes the last two entries from history and appends the current error again. Since `main` already appended the current result, two consecutive results with the same error type can satisfy the three-entry check. For repeated timeout results, that check runs before normal `CODEX_ERROR` retry routing, and the stuck-loop route sends `CODEX_ERROR` to `FATAL`. ([window](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-B-attempt1/routing_system.py:16>), [detector](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-B-attempt1/routing_system.py:142>), [stuck-loop routing](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-B-attempt1/routing_system.py:152>))

Blocking DSL state takes precedence over that detector and routes to `REPAIR_SPEC`. The repair handler increments counters and `spec_version`, but says the repair hook is not implemented. It does not change the `ExecutionInput` passed to the next `run_codex` call. Consequently, with blocking DSL state, repeated timeouts can take the repair-budget path without reaching stuck-loop routing. ([blocking-state precedence](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-B-attempt1/routing_system.py:42>), [repair handler](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-B-attempt1/main.py:102>), [unimplemented hook](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-B-attempt1/main.py:111>))

**Source-derived inference:** A retry reuses the same `ExecutionInput`; the retry handler changes counters but not its metadata. So another subprocess call uses the same configured timeout. Also, if a retry is selected on the last permitted cycle, the handler increments `total_cycles` to the maximum; the loop then exits before another subprocess call. ([retry handling](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-B-attempt1/main.py:91>), [loop and stop](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-B-attempt1/main.py:29>), [cycle limit check](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-B-attempt1/contracts.py:272>))

### Runtime boundary

The checked-in code establishes that a timeout value is passed to `subprocess.run` and that a raised `TimeoutExpired` is converted into the result described above. It does not implement a timer or explicitly terminate a process. The precise timeout enforcement, partial-output behavior, and any process or process-group cleanup depend on Python’s subprocess implementation and the operating system; this repository alone does not establish those details, so I have not asserted them.
