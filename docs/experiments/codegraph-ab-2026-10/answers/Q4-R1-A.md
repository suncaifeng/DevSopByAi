## Routing and recovery

- `main` stores each result in `state.history` before calling the router. The router first handles success, then blocking DSL state, then stuck-loop detection, and only afterward dispatches by error type. Thus a timeout’s `CODEX_ERROR` can be routed to spec repair first if the DSL is marked blocked. ([main loop](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-A-attempt1/main.py:36>), [routing order](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-A-attempt1/routing_system.py:33>))
- Otherwise, `CODEX_ERROR` gets `RETRY_CODEX` when both the cycle and retry budgets allow it; when they do not, it gets `FATAL`. The timeout handler does not distinguish a workload timeout from a transient error, so the router applies this general `CODEX_ERROR` policy. ([CODEX_ERROR route](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-A-attempt1/routing_system.py:86>), [budget predicate](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-A-attempt1/contracts.py:270>))
- **Control-flow inference:** in the `main` path, the current result is already in history when stuck detection runs. The detector takes the last two history entries and appends the current error again. Consequently, two adjacent matching errors in `main`’s history can satisfy its three-item comparison. A repeated `CODEX_ERROR` then routes to `FATAL`, because the stuck-loop repair branch covers only `TEST_FAILURE`, `SPEC_CONFLICT`, and `VALIDATION_ERROR`. ([history append](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-A-attempt1/main.py:39>), [detector](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-A-attempt1/routing_system.py:142>), [stuck-loop routing](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q4-R1-A-attempt1/routing_system.py:152>))

## Cycle stop and runtime boundary

- When a retry route is applied, `main` rechecks the retry budget, increments `codex_retries` and `total_cycles`, then continues. The loop runs only while `total_cycles < max_total_cycles`; after a continue reaches the limit, it prints the max-cycle stop message and returns. The initial state starts at zero, and the counter increments on accepted retry or repair routes, so the source does not simply count every invocation as one cycle.
