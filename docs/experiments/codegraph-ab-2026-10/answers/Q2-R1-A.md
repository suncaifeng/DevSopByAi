## Route decision and counters

For a failed result, `route_decision` checks in this order: blocking DSL state, stuck loop, then error type. Thus a blocking DSL state takes precedence over the error-specific routes. ([routing_system.py:33](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/routing_system.py:33), [routing_system.py:42](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/routing_system.py:42), [routing_system.py:51](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/routing_system.py:51))

| Failed result | Route when applicable |
|---|---|
| Blocking DSL state | `REPAIR_SPEC` |
| `TEST_FAILURE` | `RETRY_CODEX` if retry budget allows; otherwise `REPAIR_SPEC` if repair budget allows, else `FATAL` |
| `SPEC_CONFLICT` | `REPAIR_SPEC` if repair budget allows, else `REGENERATE_SPEC` |
| `VALIDATION_ERROR` | `REPAIR_SPEC` if repair budget allows, else `FATAL` |
| `CODEX_ERROR` | `RETRY_CODEX` if retry budget allows, else `FATAL` |
| `ENV_ERROR` or `UNKNOWN` | `FATAL` |

These branches are in `route_decision` and its repair helpers. A stuck-loop result changes some outcomes: repeated `TEST_FAILURE`, `SPEC_CONFLICT`, or `VALIDATION_ERROR` goes through repair-or-regenerate; other repeated error types go to `FATAL`. ([routing_system.py:54](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/routing_system.py:54), [routing_system.py:70](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/routing_system.py:70), [routing_system.py:78](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/routing_system.py:78), [routing_system.py:86](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/routing_system.py:86), [routing_system.py:103](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/routing_system.py:103), [routing_system.py:152](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/routing_system.py:152))

When `main` applies `RETRY_CODEX`, it checks `total_cycles < max_total_cycles` and `codex_retries < max_codex_retries`. If allowed, it increments both counters and continues. For `REPAIR_SPEC`, it checks the cycle and repair limits; if allowed, it increments `spec_repairs`, `spec_version`, and `total_cycles`, then continues. If either budget check fails, `main` sets `total_cycles` to the maximum, ending the loop. ([contracts.py:270](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/contracts.py:270), [contracts.py:277](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/contracts.py:277), [main.py:91](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/main.py:91), [main.py:102](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/main.py:102))

## Inference and limits

For a concrete first-failure example, suppose the subprocess exits nonzero and its output is classified as `TEST_FAILURE`, with no blocking DSL state or stuck loop and available retry budget. The source then yields `RETRY_CODEX`; applying that route changes the default initial counters from retries `0`, repairs `0`, cycles `0` to retries `1`, repairs `0`, cycles `1`. The retry passes the same `execution_input` to `run_codex`. ([main.py:52](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/main.py:52), [main.py:97](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/main.py:97), [main.py:36](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/main.py:36))

One notable source detail affects repeated failures: because `main` appends the current result before routing, `_detect_stuck_loop` reads history that already includes that result, then appends the current error again. With two consecutive identical errors, its three-item check can therefore succeed on the second failure. That is a source-derived control-flow observation; whether actual executions produce identical errors depends on runtime output. ([main.py:40](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/main.py:40), [routing_system.py:142](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/routing_system.py:142), [routing_system.py:146](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/routing_system.py:146))

A `REPAIR_SPEC` route increments counters but does not run a repair hook: `main` says that hook is not implemented, and it does not replace `execution_input.dsl` here. So source confirms the next call uses the same input object; it does not establish what the subprocess will do on that next call. ([main.py:56](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/main.py:56), [main.py:108](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-A-attempt1/main.py:108))

Finally, the router uses `status` and `error_type`; it does not branch on `result.tests`. Thus the test-result heuristic alone does not determine the route. A zero exit code routes to `SUCCESS` before error-specific checks.
