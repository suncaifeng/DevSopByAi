## Source-derived inferences and limits

- **Spec repair is a placeholder.** The repair branch increments counters and `spec_version`, but says the repair hook is not implemented. The next iteration still passes the original `execution_input` to `run_codex`, which serializes `execution_input.dsl`; no replacement DSL is applied in this repository. [main.py:102](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q1-R2-B-attempt1/main.py:102) [main.py:36](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q1-R2-B-attempt1/main.py:36) [codex_run.py:138](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q1-R2-B-attempt1/codex_run.py:138)

- **The stuck-loop window appears shorter in practice than its constant suggests.** `main` appends the current result to history before routing; the detector then reads recent history and appends the current error again. With `STUCK_LOOP_WINDOW = 3`, two consecutive matching failures can therefore satisfy the three-element check. This is a source-based inference; I did not run the code. [main.py:39](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q1-R2-B-attempt1/main.py:39) [routing_system.py:16](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q1-R2-B-attempt1/routing_system.py:16) [routing_system.py:142](/tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q1-R2-B-attempt1/routing_system.py:142)

- **A success exit can take priority over negative test text.** The adapter sets status from the exit code and only classifies errors for nonzero exits. The router then accepts `SUCCESS` before checking failure evidence; result validation requires a test outcome when tests are marked as run, but does not require that outcome to be passing. Thus a zero exit with output indicating failed tests can still route to success.
