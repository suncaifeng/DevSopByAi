## Route and counter behavior

The router checks conditions in this order ([`routing_system.py`](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-B-attempt1/routing_system.py:33>)):

- A successful result routes to `SUCCESS`.
- For a failed result, blocking DSL state routes to `REPAIR_SPEC` before error-type handling ([`_dsl_has_blocking_state()`](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-B-attempt1/routing_system.py:121>)).
- Otherwise, a detected repeated-error loop is handled before the individual error branches ([`_detect_stuck_loop()`](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-B-attempt1/routing_system.py:142>)).
- `TEST_FAILURE` and `CODEX_ERROR` route to `RETRY_CODEX` when retry budget remains. Without retry budget, test failures may route to repair or fatal; runtime errors route to fatal ([`routing_system.py`](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-B-attempt1/routing_system.py:54>), [`routing_system.py`](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-B-attempt1/routing_system.py:86>)).
- `SPEC_CONFLICT` routes to repair if possible, otherwise regeneration. `VALIDATION_ERROR` routes to repair if possible, otherwise fatal. `ENV_ERROR` and `UNKNOWN` route to fatal ([`routing_system.py`](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-B-attempt1/routing_system.py:70>), [`routing_system.py`](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-B-attempt1/routing_system.py:78>), [`routing_system.py`](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-B-attempt1/routing_system.py:103>)).

Retry eligibility requires both `total_cycles < max_total_cycles` and `codex_retries < max_codex_retries`; repair eligibility similarly checks the cycle and repair limits ([`contracts.py`](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-B-attempt1/contracts.py:270>)). The defaults are 10 total cycles, 2 Codex retries and 1 spec repair ([`RunPolicy`](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-B-attempt1/contracts.py:71>)).

After a `RETRY_CODEX` decision, `main()` checks eligibility again; if allowed, it increments `codex_retries` and `total_cycles`, then loops with the same `execution_input` ([`_apply_retry_code_route()`](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-B-attempt1/main.py:91>)). After `REPAIR_SPEC`, it increments `spec_repairs`, `spec_version` and `total_cycles` if allowed. The source says the repair hook that would replace the DSL is not implemented; if the budget is exhausted, `main()` sets `total_cycles` to its maximum and stops ([`_apply_repair_spec_route()`](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-B-attempt1/main.py:102>)). `REGENERATE_SPEC`, `ASK_USER` and `FATAL` return from `main()`.

## Source-implied caveat and runtime uncertainty

There is a history interaction that affects stuck-loop routing: `main()` appends the current result before calling the router, while `_detect_stuck_loop()` reads the last two history errors and appends the current error again. With ordinary Python list behavior, two consecutive executions with the same error can therefore supply three identical entries to the check, despite `STUCK_LOOP_WINDOW = 3` ([`main.py`](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-B-attempt1/main.py:39>), [`routing_system.py`](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-B-attempt1/routing_system.py:16>), [`routing_system.py`](</tmp/devsopbyai-codegraph-ab-measured-worktrees-20261002/Q2-R1-B-attempt1/routing_system.py:142>)).

For example, a first failed process result classified as `CODEX_ERROR` routes to `RETRY_CODEX` if its retry budget is available; with default policy and initial state, `main()` then increments retries and cycles to 1. That is a conditional source-defined path, not a claim about an actual run. The actual classification and final route depend on the execution input, subprocess exit or exception, captured output, DSL state, and policy. `run_codex()` itself does not validate the input; the validation is guaranteed only on the `main()` path described above.
